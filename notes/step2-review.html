00 クラスタの構造(control-plane と worker)

Step1で作った3ノードのkindクラスタが、内部でどう役割分担しているか。

Kubernetesクラスタは「頭脳」にあたるcontrol-planeと、「実行部隊」にあたるworkerノードに分かれている。 すべての通信はkube-apiserverという単一の窓口を経由し、末端のPodを直接触りに行くことはない。

01 Namespaceという区画

物理的な隔離ではなく、同じNode群・同じネットワークを共有したままの「論理的な仕切り」。

kind クラスタを作った直後から kube-system や default など複数のNamespaceが存在していた。 そこに今回 sample-app という区画を追加し、以降の全リソースをそこに所属させている。

02 Deployment → ReplicaSet → Pod

「3つ保て」という宣言から、実際のPodが生成・監視され続けるまでの制御ループ。

Deployment は自分でPodを直接作らない。「replicas: 3 を維持しろ」という指示を ReplicaSet に渡し、実際にPodの数を数えて過不足を調整するのはReplicaSetの仕事になっている。

03 ラベルセレクタによる疎結合

DeploymentはPodを「作る」、ServiceはPodを「選ぶ」。この2つは別の仕組み。

Serviceは「Deploymentが作ったPod」を見ているわけではない。selector: app: sample-app というラベル条件に一致する Podであれば、誰が作ったPodでも自動的にトラフィックの転送先に含める。

06 ファイル解説

上の図で説明した仕組みが、実際のYAMLのどの行に対応しているか。

apps/sample-app/namespace.yaml 
apiVersion: v1
kind: Namespace
metadata:
  name: sample-app
  1. kind: Namespace — クラスタ内に論理区画を作る(①のオレンジ枠)
  2. name: sample-app — 以降の全リソースがこの名前をnamespace欄に指定して所属する
apps/sample-app/configmap.yaml 
apiVersion: v1
kind: ConfigMap
metadata:
  name: sample-app-html
  namespace: sample-app
data:
  index.html: |
    <!DOCTYPE html>
    <html>...</html>
  1. namespace: sample-app — ①で作った区画への所属を明示
  2. data.index.html — キー名がそのままファイル名になり、値がファイルの中身になる(④でPodにマウントされるもの)
  3. | (リテラルブロックスカラー) — 改行を保ったまま複数行の文字列を書けるYAML記法
apps/sample-app/deployment.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-app
  namespace: sample-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx
          image: nginx:1.27-alpine
          ports:
            - containerPort: 80
          volumeMounts:
            - name: html
              mountPath: /usr/share/nginx/html
      volumes:
        - name: html
          configMap:
            name: sample-app-html
  1. spec.replicas: 3 — 「望ましいPod数」の宣言(②)
  2. spec.selector.matchLabels — ReplicaSetが「自分の管理対象」とみなすPodの条件
  3. template.metadata.labels — 実際に生成されるPodに貼られるラベル。selectorと一致しないとDeploymentがエラーになる(③の土台)
  4. volumeMounts / volumes — ConfigMapをファイルとしてコンテナに配線する部分(④)
apps/sample-app/service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: sample-app
  namespace: sample-app
spec:
  type: NodePort
  selector:
    app: sample-app
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080
  1. type: NodePort — 全ノードの指定ポートで外部公開するService種別
  2. spec.selector — Deployment名やPod名は一切見ず、ラベルだけでPodを動的に選ぶ(③)
  3. nodePort: 30080 — kindのextraPortMappingsで用意したホスト側30080番と合わせた数字(⑤)
